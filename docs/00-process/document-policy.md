# 文档管理制度

本制度规定本项目文档的分类、生命周期、编号、命名与变更联动规则。
**硬性约束见 [AGENTS.md](../../AGENTS.md)；本文件是执行细则。**

---

## 1. 目的

让任何人在任意时刻都能回答三个问题：

1. 项目的**权威说法**在哪一份文件里？
2. 这份文件现在**是否可信**（状态）？
3. 我改了这个功能，**还需要改哪些文件**？

---

## 2. 文档分类与职责

| 分类 | 目录 | 回答的问题 | 判断依据 |
|---|---|---|---|
| 流程规范 | `00-process/` | 我们应该怎么做？ | 与具体功能无关，长期有效 |
| 产品设计 | `01-product/` | 做什么、给谁、什么交互、怎么算完成？ | 描述用户可感知的行为 |
| 架构设计 | `02-architecture/` | 内部怎么实现、为什么这么选？ | 描述系统内部结构 |
| 决策记录 | `02-architecture/adr/` | 当初为什么这么决定？ | 一决策一文件，不可修改 |
| 接口契约 | `03-api/` | 字段叫什么、什么类型、什么语义？ | 可被代码与测试直接引用 |
| 工程规范 | `04-engineering/` | 代码怎么写、怎么测、怎么发？ | 约束实现方式 |
| 归档 | `99-archive/` | 历史上曾有过什么？ | 不再生效 |

**判定口诀**：用户能看见的 → `01-product`；只有开发者关心的 → `02-architecture`；跨进程/跨端传的东西 → `03-api`。

---

## 3. 生命周期

```
draft ──评审通过──> approved ──被取代──> superseded ──清理──> 99-archive/
  │                    │
  └──放弃──> 99-archive/└──失效──> archived
```

| 状态 | 含义 | 修改规则 | 能否作为实施依据 |
|---|---|---|---|
| `draft` | 起草中 | 自由修改 | 否 |
| `review` | 待评审 | 只按评审意见改 | 否 |
| `approved` | 已定稿 | **不允许修改内容** | 是 |
| `superseded` | 被新文档取代 | 冻结，仅保留指针 | 否 |
| `archived` | 已废弃 | 冻结 | 否 |

规则：

1. `approved` 文档需要改动时，**新建**一份替代文档，把旧文档状态改为 `superseded`，并在两份文件的文档头互相指向。
2. 补错别字、修链接这类不改语义的编辑，允许直接改 `approved` 文档，但要在末尾「变更记录」记一行。
3. 文档被 `superseded` 满 3 个月且无人引用，移入 `99-archive/`。

---

## 4. 文档头与末尾（强制）

每份文档**开头**：

```markdown
> **状态**：draft | review | approved | superseded | archived
> **版本**：v0.1
> **最后更新**：YYYY-MM-DD
> **取代/被取代**：无 / 见 xxx.md
```

每份文档**结尾**：

```markdown
## 变更记录

| 版本 | 日期 | 变更 |
|---|---|---|
| v0.1 | YYYY-MM-DD | 初稿 |
```

版本号规则：`v0.x` 起草期，`v1.0` 首次定稿，之后小改动 `v1.1`，结构性改动 `v2.0`。

例外（仅两类）：

- **ADR** 不可修改，因此**不写**「变更记录」；变更由文档头的「取代/被取代」字段表达。
- 根目录的 `README.md` / `AGENTS.md` 不设变更记录，其变更统一记在 `CHANGELOG.md`。

---

## 5. 编号

| 前缀 | 用途 | 分配位置 | 复用 |
|---|---|---|---|
| `F` | 功能 | `feature-registry.md` | **永不复用** |
| `D` | 决策摘要 | `design.md` §1 | 永不复用 |
| `ADR-` | 架构决策记录（4 位序号，按创建顺序递增） | `adr/` 文件名 | 永不复用 |
| `Q` | 开放问题 | `design.md` 开放问题章 | 永不复用 |

删除功能后，编号作废并从登记表移除，**不补号、不复用**。这是为了让 `CHANGELOG` 与提交历史里的旧编号永远可追溯。

---

## 6. 命名

- 文件：小写 `kebab-case` + `.md`，例 `rest-contract.md`。
- ADR：`ADR-0001-<短横线英文摘要>.md`，例 `ADR-0003-script-runtime-quickjs-webview.md`。
- 功能规格（拆分时）：`features/f07-collect.md`（编号小写 + 英文短名）。
- 禁止：中文文件名、空格、日期前缀（除 ADR 序号）、`final`/`new`/`v2` 这类残留在名字里的版本词。

---

## 7. SSOT 与引用

1. 每个主题只有一份权威表述（清单见 `AGENTS.md` §2.1）。
2. 其它文档需要引用时，只能写**链接 + 一句概述**，不得复制表格、复制字段定义。
3. 引用必须用相对路径，且必须能点开：

   ```text
   同目录：  [design.md](design.md)
   跨目录：  [design.md](../01-product/design.md)
   指向根：   [AGENTS.md](../../AGENTS.md)
   ```
4. 代码里引用文档，只允许引用**章节锚点**，不复制内容。例：`// 见 docs/01-product/design.md「5.5 图集阅读器」`

## 8. 功能增删联动协议

> `AGENTS.md` §3 定义了**规则与必改清单**；本节定义**具体怎么改**。

### 8.1 新增功能

1. 从 `feature-registry.md` 取下一个空闲编号（最大号 +1，不复用）。
2. 在 `design.md` §5 表格加一行：编号 / 功能 / 优先级 / 说明。
3. 在 `design.md` 对应功能章（或新开小节）写清：入口、交互、数据来源、边界、**验收标准**。
4. 若"技术架构"章节需要调整，同步修改；若引入了不可回退的技术选择，新增 ADR。
5. `feature-registry.md` 加一行：编号、名称、优先级、状态 `planned`、里程碑、关联章节。
6. `CHANGELOG.md` → `Added`，引用 `F` 编号。
7. 若 `docs/README.md` 索引需要新增文档，同步登记。

### 8.2 删除功能

1. `design.md` §5 **移除**该行；该功能的详细小节**整段移除**（不保留注释掉的段落）。
2. `design.md` 末尾「变更记录」写一行：`删除 F07 收藏：原因 xxx，影响 xxx`。
3. `feature-registry.md` 该行状态置为 `dropped`，**保留行不删**（保证编号可追溯）。
4. `CHANGELOG.md` → `Removed`，引用编号并写明原因。
5. 若该功能有独立规格文档（`features/`），文档头状态改为 `archived` 并移入 `99-archive/`。
6. 若删除导致架构简化，新增一条 ADR（不要改旧 ADR）。

### 8.3 改名 / 改范围

按 8.2 的"记录"步骤 + 8.1 的"登记"步骤：旧编号保留并标 `dropped`，新范围用新编号或原编号但必须在「变更记录」写明。**不允许静默改变一个 `F` 编号的含义。**

### 8.4 何时拆分功能规格文档

满足任一条件，把 `design.md` 里的功能小节拆到 `docs/01-product/features/`：

- 单个功能小节超过 60 行
- 该功能有独立的交互流程图 / 状态机
- 该功能进入开发阶段，需要独立的验收清单

拆分后 `design.md` 该小节只留 3–5 行摘要 + 链接；`docs/README.md` 登记新文件。

## 9. 提交前的文档检查清单

- [ ] 改了功能？→ `design.md` + `feature-registry.md` + `CHANGELOG.md` 三处都动了
- [ ] 新文档有文档头？有变更记录？已在 `docs/README.md` 登记？
- [ ] 没有第二份复制内容（该链接的写成链接了）
- [ ] 没有在根目录新增 Markdown
- [ ] 文件名符合命名规范
- [ ] 失效链接为 0
- [ ] 涉及决策变化？→ 新增 ADR，未修改旧 ADR
