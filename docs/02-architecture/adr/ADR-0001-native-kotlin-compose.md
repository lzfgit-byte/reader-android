# ADR-0001：采用原生 Kotlin + Jetpack Compose

## 状态

`approved`（不可修改；决策变化请新建 ADR 并在头部标注取代）

## 背景

GHS Mobile 需要覆盖三类重负载场景：

1. **图集阅读**：一页图组可达 300 张、单图可达 8000px 高，需要精细控制图片采样、内存峰值与连续滚动的手势嵌套；
2. **视频播放**：mp4 与 m3u8（含加密分片），需要精确 Seek、横屏全屏、画中画、后台播放与音频焦点；
3. **规则引擎**：需要在应用内驱动无头 `WebView`、注册自定义数据源、运行常驻回环代理。

这三类都对平台能力有较深的要求，选型会直接影响 M2–M4 的可行性与体验上限。

## 备选方案

| 方案 | 说明 |
|---|---|
| A. Kotlin + Jetpack Compose | 原生实现，直接使用平台能力 |
| B. 跨平台框架 | 一套代码覆盖 Android/iOS（Flutter 或 KMP + Compose Multiplatform） |
| C. WebView 壳 | 直接加载目标站网页，只做外壳 |

## 决策

采用 **方案 A：Kotlin + Jetpack Compose**。

配套：Media3(ExoPlayer) 播放、Coil 图片、Room 持久化、OkHttp 网络、Koin 依赖注入、Coroutines/Flow 并发与状态。

## 理由

1. **视频上限**：Media3 原生提供 HLS/DASH、多音轨、精确 Seek、MediaSession、画中画。跨平台方案的播放器在 HLS 与后台播放上普遍需要平台通道补齐，最终仍要写 Kotlin。
2. **引擎集成**：无头 `WebView` 控制、自定义 `DataSource`、本地回环 server 都是平台级 API；跨平台方案会把这些能力推回原生层，反而增加一层桥接成本与故障面。
3. **内存控制**：长图是否 OOM 取决于解码参数（`inSampleSize`、局部分块）与图片库的缓存策略。原生栈可以逐层控制，跨平台栈在图片解码上的可调粒度更粗。
4. **手势与滚动**：Compose 的 `LazyColumn` / `HorizontalPager` + 嵌套滚动能精确表达"边缘滑动调亮度/音量、中部滚动翻页"这类复合手势。
5. **单一技术栈**：v1 只做 Android，跨平台带来的第二端收益在本期为零，而复杂度立即发生。

## 后果

**正面**

- 视频、阅读、引擎三处均可用平台原生能力，体验上限最高
- 无跨语言桥接，调试链路短
- 可直接使用前台服务、通知、画中画等系统能力

**负面**

- 后续若要做 iOS，需另起一套实现，业务逻辑无法直接复用
- 全部 UI 需自研，M2–M4 工作量集中在渲染与手势调试
- 依赖 Compose 版本演进（保持稳定版即可规避）

## 缓解

- 领域模型与状态管理集中在 `:core:*` 模块，未来若要跨平台，可先把这块下沉到 KMP
- 交互规格在设计文档 §5 中逐条写明验收标准，避免"边做边改"导致返工
