# ADR-0018：来源自己声明代理策略，设备只留开关与代理列表

## 状态

`approved`

## 背景

[ADR-0009](ADR-0009-proxy-whitelist-single-decision.md) 把"白名单 = 直连"做成设备侧设置，理由是"单点判定、两通道一致"。落地后发现三个问题：

1. **白名单是"设备级"的，但需求是"来源级"的**：同一个代理下，站点 A 必须走代理、站点 B 直连更好。写在一份全局白名单里，切来源时用户得手动改名单；
2. **白名单与强制名单都要用户手写域名**，而"这个来源要不要代理"其实来源作者最清楚，写在配置里天然随配置走；
3. **设置页被自由文本撑大了**：白名单、强制名单两个输入框加一个「应用」按钮，和"开关 + 代理列表"两件事混在一起，理解成本高。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 保留白名单，只加来源开关 | 设备白名单继续存在，配置加 `isProxy` | 两套机制并存：用户仍要维护白名单，规则冲突时难以解释 |
| B. 白名单整体换成来源声明 | 设备只留开关 + 代理列表；`isProxy` 默认 true、`forceProxy` 补"必须代理"的地址 | 设置页最小，规则跟着配置走；个别 URL 想直连时没有设备级入口 |
| C. 白名单 + 来源声明都留 | 两者都生效 | 判定链变长、语义重复，文档与排障成本最高 |

## 决策

采用 **方案 B**：

1. **设备侧只保留两件事**：代理总开关 + 代理列表（多条、同一时刻一条生效）。删除白名单、强制名单与「应用」按钮；
2. **来源声明**：配置新增 `isProxy`（boolean，默认 `true`）与 `forceProxy`（string[]，默认 `[]`）；
3. **判定顺序固定为**：总开关关 / 端点不完整 → 直连；目标是代理自己 → 直连；命中 `forceProxy` → 走代理；其余按 `isProxy`；
4. **仍是一处判定**：`ProxyRules.shouldProxy(host, port)` 同时被 OkHttp `ProxySelector`、WebView 覆盖（每次导航前按目标地址算）与图片兜底使用；来源策略由进程级 `SiteProxyPolicy` 提供，切来源即换策略；
5. 代理总开关是**最终闸门**：关掉时任何来源都直连，`forceProxy` 也不生效。

## 理由

1. **"要不要代理"属于来源知识**：写配置的人知道站点在哪个网络下能通，设备设置不该承载它；
2. **设置页回到两件事**：开关管"我用不用代理"，列表管"用哪条"，用户不用再理解白名单/强制名单的优先级；
3. **默认值偏向保守**：不写 `isProxy` 就走代理（与旧行为一致：未配置白名单时全部走代理），只有明确知道"这个站要直连"的作者才写 `false`；
4. **`forceProxy` 覆盖真实场景**："站点直连更稳、但图床/CDN 必须过代理"——这种混合拓扑用一条 `forceProxy` 就能表达，而设备白名单表达不了。

## 后果

**正面**

- 设置页只剩开关与代理列表，交互与文案都变短
- 切来源即切策略，不需要用户改设备设置
- 判定仍是纯函数，可用单测穷举（默认/显式直连/强制命中/端口/自环/开关关闭）

**负面（必须正视）**

- 设备级"个别域名直连"的能力没有了：需要直连就必须在对应来源里声明 `isProxy: false`
- 来源声明写在配置里，改配置要重新导入（不是拨一下开关）
- 旧版本存过的 `proxy_whitelist` / `proxy_force` 键仍在库里，但不再读取——升级后用户不会"半生效"

## 缓解

- 设置页明确写出「来源级策略写在配置里」，并显示当前来源判定（直连 / 走代理 / 强制名单条数）
- 会话建立时把来源策略打进日志（`site proxy isProxy=… forceProxy=…`），排障时一眼可见
- 判定表驱动单测覆盖六种分支，另用本地站点 + 本地代理做真机 A/B
