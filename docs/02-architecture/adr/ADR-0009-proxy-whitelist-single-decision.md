# ADR-0009：白名单是唯一的代理判定点，转发代理进入 v1

## 状态

`superseded by ADR-0018`（2026-10-27：白名单模型被来源级 `isProxy` / `forceProxy` 取代）

## 背景

[ADR-0008](ADR-0008-http-proxy-two-channels.md) 把代理定为两条通道共用，但留了两个待决问题：

1. **认证代理 + WebView** 被排到 v1.1（因为 WebView 的 `ProxyController` 不支持代理认证）；
2. **绕过列表** 在两条通道各实现一遍（OkHttp 自己判断、WebView 用 `addBypassRule`），两处规则容易漂移。

后续需求明确了三点：代理能力**必须在第一版可用**、**未配置时代理关闭走直连**、需要**白名单**（命中白名单的请求不走代理）。

如果沿用 ADR-0008 的阶段划分，"认证代理 + WebView" 在 v1 不可用；而白名单在两处各判一次，会出现"某个域名在列表页走直连、在兜底页却走了代理"的不一致。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 保持 ADR-0008 | 认证代理的 WebView 留到 v1.1；白名单两处各判 | 实现最省，但 v1 存在能力缺口与判定漂移风险 |
| B. 转发代理进 v1，白名单双实现 | v1 支持认证；OkHttp 走 ProxySelector，WebView 用 `addBypassRule` | 能力完整，但两套白名单逻辑仍需同步维护 |
| C. 转发代理进 v1，白名单单点判定 | WebView 恒指向本地转发代理，由转发代理执行白名单；OkHttp 用同一判定函数 | 能力完整且语义一致；代价是转发代理成为必需品 |

## 决策

采用 **方案 C**：

1. **转发代理成为 v1 的一部分**：应用内 `127.0.0.1:随机端口` 的 HTTP 转发代理，支持绝对 URI 转发与 `CONNECT` 隧道，向上游补 `Proxy-Authorization`；
2. **白名单是唯一判定点**：`ProxyDecision.shouldProxy(host, port)` 一处实现，OkHttp 通过 `ProxySelector` 调用它，转发代理内部同样调用它；
3. **WebView 恒指向本地转发代理**（不依赖 `addBypassRule`），因此白名单对 WebView 的效果与对应用请求完全一致；
4. **未配置代理即直连**：代理关闭时不启动转发代理、不设置 WebView 代理覆盖、`ProxySelector` 返回 `NO_PROXY`；
5. 若 `WebViewFeature.PROXY_OVERRIDE` 不可用，设置页显式标注"当前 WebView 不支持代理"，其余通道不受影响。

## 理由

1. **一致性比少一层跳转重要**：白名单错判的表现是"有的页面通、有的不通"，用户无法自行排查；单点判定从根上消除这种可能。
2. **转发代理本来就要写**：`CONNECT` 隧道是"认证代理 + HTTPS"的必要条件，早做比晚做更省——晚做会导致 v1 的所有 WebView 测试都在无认证代理下进行，认证路径的 bug 推迟暴露。
3. **OkHttp 不必绕行**：应用请求直连上游代理（一次跳转），只有 WebView 走本地转发，避免给全部请求加一跳。
4. **"未配置即直连"是降低风险的关键**：默认状态下不引入任何新故障点，代理是纯增量能力。

## 后果

**正面**

- v1 即覆盖「认证代理 + WebView」组合
- 白名单只有一处实现，可用单测穷举
- 关闭代理时行为与没有该功能完全一致

**负面（必须正视）**

- 转发代理成为 v1 交付项（CONNECT 隧道、并发、超时、连接复用都要做）
- WebView 的流量多一跳本地回环，长连接场景需注意开销
- 转发代理要正确处理分块传输、`CONNECT` 双向管道与异常断开
- `ProxyController` 是进程级的，切换配置需重新下发覆盖

## 缓解

- 转发代理只在"代理已配置且 WebView 通道启用"时启动，其余情况不占用端口
- 白名单判定抽成纯函数 + 表驱动单测（域名/子域/通配/CIDR/端口）
- 代理或白名单变更后清空 HTML/图片缓存，并用连通性检测确认生效
- 转发代理的连接与线程上限、单请求超时与主通道配置共用
