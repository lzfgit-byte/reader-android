# ADR-0010：人机校验用独立顶层 Activity，校验后带 Cookie 重试

## 状态

`approved`

## 背景

取页可能拿到的不是内容，而是**人机校验页**（Cloudflare 挑战、reCAPTCHA、hCaptcha 等）。此时：

- 解析必然失败（挑战页里没有目标数据）；
- 只有真人能在浏览器环境里完成校验；
- 校验通过后，通行凭证落在 **Cookie** 上。

产品要求是：**在最顶层弹出校验窗口，用户完成后继续加载并拿到真实 HTML**。

三个约束决定了实现方式：

1. **必须顶层**：请求可能来自任何位置——首页列表、详情页、阅读器、后台预热，甚至网页调试台（引擎在设备上跑，人不在应用界面里）。页面内的浮层依赖导航栈与前台 Activity，靠不住。
2. **必须是真浏览器**：挑战页需要完整 JS 与渲染，无头 WebView 不可见、无法交互。
3. **凭证要回流**：校验产生的 Cookie 必须进入主通道（OkHttp）的 Cookie 存储，否则"通过一次、下次还要过"。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 页面内浮层（Compose Dialog / Overlay） | 在 NavHost 之上叠一个全屏组件 | 实现自然，但**跳不出当前页面**：后台请求、调试台请求、跨 Tab 触发时无处可叠 |
| B. 独立 Activity（独立任务栈） | `ChallengeActivity`，`NEW_TASK` + 独立 task affinity | 从任何状态都能弹；需处理返回栈与后台启动限制 |
| C. 通知 + 用户点开 | 只发通知，用户点开才进校验页 | 最稳，但即使应用在前台也要多一次点击，体验差 |
| D. 让用户去系统浏览器完成 | 跳转外部浏览器 | 拿不回 Cookie，无法延续请求 |

## 决策

采用 **方案 B 为主 + 方案 C 兜底**：

1. **前台**：检测到挑战 → 直接启动 `ChallengeActivity`（`NEW_TASK`、独立 task affinity、`excludeFromRecents`），从下往上滑入，页面内容可见地让位；
2. **后台**：Android 10+ 禁止后台直接启动 Activity → 发高优先级通知（"需要完成人机校验"），点击通知进入同一 Activity，同时把请求挂起等待；
3. **校验完成后**：
   - 先做 **Cookie 双向同步**（WebView `CookieManager` ⇄ OkHttp `PersistentCookieJar`）；
   - **优先用 OkHttp 带同一 Cookie 重试原 URL**（结果与主通道完全一致，含同一 UA/代理/头）；
   - 重试仍失败才回落到"取 WebView 的 `outerHTML`"（浏览器渲染后的 DOM 可能与原始 HTML 不同，只作兜底）；
4. **单飞合并**：同一 host 同时最多一个窗口，其余请求排队共享结果，避免弹窗风暴；
5. **不缓存挑战页**：挑战响应不写入 HTML 缓存，并作废该 URL 的既有缓存条目。

## 理由

1. **Activity 是唯一可靠的"最顶层"**：它独立于导航栈，能从服务/后台请求/任意 Tab 弹起；Dialog 与 Compose Overlay 都绑在当前界面。
2. **优先 OkHttp 重试而非直接取 DOM**：主通道拿到的是**原始 HTML**，与解析脚本的假设一致；WebView 的 `outerHTML` 是渲染后的 DOM（可能被 JS 改写、可能有注入节点），拿它解析会让"同样的配置在不同通道表现不同"。
3. **单飞是必须的**：一屏列表可能并发 6 个请求同时撞上挑战，不合并就是连弹 6 个窗口。
4. **不缓存挑战页**：否则下次直接命中缓存的挑战页，用户会看到"一直失败、清缓存才好"。

## 后果

**正面**

- 任何触发源都能弹窗，不依赖当前界面
- 校验通过后与主通道行为一致（同一 OkHttp 客户端）
- 一次通过长期有效（Cookie 持久化）

**负面（必须正视）**

- **后台启动限制**：应用在后台时只能发通知，用户不点就一直等到超时（`E-CHALLENGE-004`）
- **Activity 生命周期复杂**：进程可能在中途被回收，需用可持久化的 `ChallengePending` 记录恢复状态
- **Cookie 双向同步易错**：Android WebView 的 Cookie 存储与 OkHttp 各有一套，必须显式桥接并 `flush()`
- **安全面**：窗口内允许用户交互，要限制只能导航到同 host，禁止外部 scheme

## 缓解

- 超时默认 5 分钟，超时/取消向调用方抛明确错误码，UI 可重试
- 首页等并发场景只允许一个窗口，其余请求排队（排队时长计入超时）
- 窗口内跨站跳转与外部 scheme 一律拦截或二次确认
- 校验完成后立刻作废缓存并重新抓取，日志记录"命中校验 → 通过 → 重试成功"的耗时
