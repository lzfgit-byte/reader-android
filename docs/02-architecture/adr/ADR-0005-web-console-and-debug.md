# ADR-0005：配置编辑放在应用内置的 Web 管理界面，应用内只做管理与只读

## 状态

`approved`

## 背景

配置是本产品的核心输入（[ADR-0002](ADR-0002-embedded-engine-dual-provider.md)）：没有配置，应用只是一个空容器。因此**配置的编写与修改必须在第一版就能用**，否则产品无法被实际使用。

编辑配置需要三种能力：输入代码（键盘、语法高亮、错误定位）、查看返回数据（大段 JSON）、反复试跑（运行 → 看结果 → 改 → 再运行）。

在手机上做这三件事的体验有硬伤：软键盘遮挡、侧栏放不下、JSON 树看不全、并排对照做不到。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 应用内编辑器 | Compose 全屏代码编辑器 + 应用内调试页 | 无需额外进程，但输入/阅读体验差，且要为移动端重写一套编辑器 UI |
| B. 内置 Web 管理服务 | 应用起 HTTP 服务，浏览器打开管理界面 | 大屏体验好、可复用成熟前端生态，但引入额外技术栈与安全面 |
| C. 外置桌面工具 | 独立桌面程序编辑，文件导入导出 | 体验好，但用户需安装第二个程序，且无法直接访问设备上的引擎 |
| D. 不做编辑 | 只能导入他人写好的配置 | 成本最低，但产品失去自举能力，违背"配置驱动"的前提 |

## 决策

采用 **方案 B**，并做两条硬性约定：

1. **编辑只在 Web 管理界面**：应用内**永久不提供**配置编辑能力（原计划的应用内编辑器取消，见设计文档 §5 与 `feature-registry.md` 的 `dropped` 记录）；
2. **管理能力两侧都有**：导入、导出、切换、启停、排序、删除在**应用内与网页端都必须可用**——因为存在"手上没有浏览器"或"socket 不方便开"的场景。

## 理由

1. **分工合理**：浏览器擅长"写与看"，设备擅长"连网与执行"。把编辑搬进浏览器后，两端各自用最擅长的能力。
2. **调试形态决定**：调试要看 JSON、比耗时、翻日志，本质是开发者工具，天然属于桌面浏览器；手机端做同样的事只能做一半。
3. **零安装**：服务由应用自己提供，用户不需要装第二个程序（区别于方案 C），也不受手机屏幕限制（区别于方案 A）。
4. **一套前端**：桌面浏览器与手机浏览器访问的是同一份页面，无需维护两套编辑 UI；应用内只保留原生管理页，职责更单一。
5. **调试 API 顺带解决自动化**：把"运行某个方法并返回 JSON"抽象成 HTTP 接口后，同一套能力可以被外部脚本复用于回归测试。

## 后果

**正面**

- 编辑体验接近桌面开发工具，且不需要安装额外程序
- 应用内的配置页可以做得极简（只有管理动作），减少移动端复杂度
- 调试接口可被外部工具复用，也为将来的 CI 回归留出入口

**负面（必须正视）**

- **新增一套技术栈**：需要维护 TypeScript/Vue 前端与构建产物打包进 assets
- **安全面扩大**：应用开始监听端口，必须处理鉴权、绑定范围、目录遍历与请求体限制（见 [web-admin-api](../../03-api/web-admin-api.md) §9）
- **版本耦合**：前端与 `/api` 必须同版本发布，旧前端不允许连新后端
- **调试接口成为稳定契约**：一旦外部工具依赖，改造成本高于内部接口

## 缓解

- 默认**仅本机**绑定，切局域网需显式确认并展示风险
- 强制 token 鉴权，扫码即用，不在日志中记录
- 前端产物随 APK 发布，不引入运行时外链
- 调试 API 与配置规范共用同一套错误码（`E-CFG-*`），降低契约漂移
