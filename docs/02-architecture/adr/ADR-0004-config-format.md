# ADR-0004：配置采用「清单 + 脚本」双段式，兼容单文件内联

## 状态

`approved`

## 背景

应用是**配置驱动的内容容器**（设计文档 §2.1）：内容来源、卡片样式、入口显隐、阅读器默认模式全部由传入的配置决定。

初版设想是"一份 JS 源文件搞定一切"——元信息与解析方法都写在同一个可执行对象里。这带来三个问题：

1. **元信息无法静态校验**：不执行脚本就读不到 `name`、`cardStyle`、`imgWidth`，配置列表页必须先跑脚本才能显示，而跑脚本有超时、内存与安全成本；
2. **错误定位差**：脚本语法错误与字段缺失混在一起，用户只看到"加载失败"；
3. **UI 无法预判**：底栏该显示哪些 Tab、卡片用哪种排布，必须在渲染前就知道，否则会出现"先按默认布局渲染再跳变"。

另一方面，纯 JSON 描述又不足以表达解析逻辑——不同来源的 DOM 结构差异极大，必须有代码。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 纯 JS 单文件 | 元信息与解析方法都在一个可执行对象里 | 简单，但元信息无法静态校验、UI 无法预判 |
| B. 纯 JSON | 只用声明式规则（选择器配置化） | 校验友好，但无法覆盖复杂来源，表达力不足 |
| C. 清单 + 脚本 | JSON 描述元信息/渲染/行为，JS 描述解析逻辑 | 两侧优势兼顾，代价是配置要两个文件 |

## 决策

采用 **方案 C**，并保留 A 作为兼容形态：

1. **清单形态（推荐）**：`config.json`（可静态校验）+ `script.js`（解析逻辑）；
2. **内联形态（兼容）**：单个 `config.js`，导入时在沙箱内做一次**限时探测执行**提取元信息，失败即拒绝；
3. 两种形态**规范化后落到同一条记录**（`config_unit`），引擎与 UI 只面对规范化结果。

## 理由

1. **静态校验成为可能**：`E-CFG-002/003/006/007/008/010/011` 全部可在不执行代码的前提下判定，导入体验从"黑盒失败"变为"指出字段与期望值"。
2. **UI 可预判**：底栏 Tab、卡片样式、页面尺寸在渲染前就是确定值，避免布局跳变（对应 UI 规范 U2）。
3. **安全面收敛**：清单是纯数据，可被安全地展示、比较、diff；只有脚本需要沙箱。
4. **兼容成本低**：内联形态只需在导入时多做一次探测执行，运行期与清单形态走同一路径。

## 后果

**正面**

- 配置可被工具处理（校验器、对比、批量导入）
- 错误信息精确到字段路径
- UI 由配置驱动的实现路径清晰

**负面**

- 配置作者要维护两个文件（可用打包工具简化，v1.1 可提供"合并为单文件导出"）
- 存在两种形态，需要明确"以规范化为准"的原则，避免实现分叉
- 内联形态的探测执行仍需沙箱，导入比清单形态慢（多一次执行）
