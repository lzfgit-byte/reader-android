# ADR-0006：配置同步采用 WebDAV，v1 只做手动同步与冲突提示

## 状态

`approved`

## 背景

配置是用户资产：写一次、多设备用、换机不丢。三个现实约束：

1. 配置里既有声明式字段（易合并）也有脚本源码（难自动合并）；
2. 用户可能同时用手机浏览器与桌面浏览器编辑；
3. 应用没有账号体系（设计文档 §3.2），不打算自建云服务。

因此需要一个**用户已有基础设施**就能承载的同步方案，而不是再引一个账号。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 只做手动文件导入导出 | 用户自己搬文件 | 零成本，但无法"多设备自动一致" |
| B. 云盘厂商 SDK | 接 Dropbox / Google Drive 等 | 每家一套 SDK 与授权流程，锁定厂商，维护成本高 |
| C. WebDAV | 标准协议，覆盖坚果云、Nextcloud、群晖、自建 | 一套实现覆盖大量服务，无厂商锁定 |
| D. Git 仓库 | 把配置当代码提交 | 适合技术型用户，但需要 token、合并冲突概念，门槛高 |

## 决策

采用 **方案 C：WebDAV**，并限定 v1 范围：

1. **单位**：一个配置文件 = 一个 `<key>.ghscfg.json`（格式见 [config-spec](../../03-api/config-spec.md) §2.4）；
2. **v1 只做手动**：测试连接、拉取、推送、双向同步由用户点击触发；
3. **冲突策略**四选一：`newer-wins` / `local-wins` / `remote-wins` / `ask`（默认 `ask`）；
4. **不做删除同步**：本地删除不传播到远端，避免误删；仅在状态中提示"远端已不存在"；
5. **自动化预留**：配置字段 `autoSync` 与"启动时/变更后"策略在 v1 落库但不启用自动执行，v1.1 打开。

## 理由

1. **覆盖率高**：WebDAV 是自建与公有云盘的共同子集，一个实现能服务绝大多数用户，不需要为每家写适配。
2. **与文件格式天然契合**：配置本来就是"一目录多文件"，WebDAV 的 `PROPFIND` / `GET` / `PUT` 足够表达；不需要元数据服务。
3. **冲突可解释**：脚本无法自动合并，因此**不假装能合并**——直接暴露冲突让用户选边，比自动合并失败更可控。
4. **不做删除传播**：删除是不可逆操作，跨设备误删代价高；宁可让用户手动清理远端。
5. **v1 不自动**：自动同步需要处理"离线队列、失败重试、并发写"三件事，收益有限而风险集中，留到 v1.1。

## 后果

**正面**

- 用户用已有的网盘即可实现多设备一致
- 无账号体系、无厂商锁定
- 同步单位与导入导出格式统一（同一份文件走两条路）

**负面**

- 凭证需加密存储（`EncryptedSharedPreferences`），仍有泄露面
- 部分 WebDAV 服务实现有差异（大小写、ETag 缺失），需要兼容处理
- 手动同步依赖用户记得点，做不到"无感一致"

## 缓解

- `ETag` 缺失时退化为 `Last-Modified` + `updatedAt` 比较
- 单条失败不中断整批，逐条返回结果，便于定位是哪个文件/哪个服务特性问题
- 同步面板常驻"上次同步时间"，提醒用户何时该点一次
