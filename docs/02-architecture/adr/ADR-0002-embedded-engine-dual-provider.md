# ADR-0002：抓取解析引擎内置在应用内，数据层支持内置/远程双模式

## 状态

`approved`

## 背景

GHS Mobile 的产品前提是**配置驱动**（设计文档 §2.2 P2）：每个来源的 DOM 结构、分页方式、防盗链策略都不同，这些差异必须收敛到用户可维护的**解析脚本**里，而不是写进 App 代码。

规则脚本要能被执行，需要三样东西：取页能力、DOM 选择器、脚本运行时。这三样既可以放在手机里，也可以放在一个独立服务里。架构必须先回答"引擎放在哪"。

同时，产品还有一条硬要求 P1：**单机自足**——用户不部署任何服务也应能完整使用。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 纯客户端 | 引擎在外部服务，App 只渲染 | 实现最省，但违背 P1：没有服务就完全不可用 |
| B. 引擎完全内置 | 抓取、解析、存储、播放全部在 App 内 | 满足 P1，但多设备共享与自动化测试缺少入口 |
| C. B + 远程模式 | 内置为主，同时支持连接自建服务 | 多一层抽象，换来共享能力与可测试性 |

## 决策

采用 **方案 C**：

1. 在 `:core:engine` 内实现完整管线：取页 → 解析 → 执行脚本 → 归一模型；
2. 抽象 `GhsRepository`，提供 `LocalRepository`（内置引擎 + Room，默认）与 `RemoteRepository`（HTTP + WS）；
3. 两种模式遵守**同一套契约**（`docs/03-api/rest-contract.md`），UI 不感知差异。

## 理由

1. **单机可用是产品底线**：P1 决定了引擎必须内置，这不是可选项。
2. **配置归用户**：引擎内置后，用户导入配置即可支持新来源，无需等待 App 发版（对应 G2）。
3. **远程模式的成本低于收益**：
   - 多设备共享同一份抓取结果与收藏历史，是真实使用场景；
   - HTTP 契约让引擎可以脱离 UI 被驱动（`curl`、自动化回归、配套工具），显著降低调试成本；
   - 引擎与 UI 解耦后，将来把引擎拆成独立进程或服务，接口无需改动。
4. **抽象成本可控**：两个实现共享同一批 DTO 与错误类型，差异集中在传输层（HTTP vs 进程内）与存储层（Room vs 服务端）。

## 后果

**正面**

- 满足"单机自足"，同时保留共享与调试通道
- 引擎层可在 JVM 单测（不依赖 Android Framework）
- 契约先行，减少 UI 与引擎之间的耦合

**负面（必须正视）**

- 复杂度显著上升：要在 Android 上解决脚本运行时、选择器兼容、反爬、视频代理四个问题
- 内存与耗电压力：无头 WebView 是 Android 的经典泄漏源
- 手机侧比服务器更容易被限流/拦截
- 安全面扩大：执行用户提供的任意脚本需要沙箱隔离

## 缓解

- **M0 先行**：先用真实规则脚本与黄金样本验证运行时可行性（[ADR-0003](ADR-0003-script-runtime-quickjs-webview.md)）
- 引擎单例 + `Mutex` 串行，消除并发状态竞争
- 兜底 WebView 最多 1 个，超时强杀并 `destroy()`
- 脚本在 QuickJS 沙箱或独立进程的 WebView 中执行，桥接 API 走白名单
- 远程模式作为**可选开关**，默认关闭，避免默认路径承担额外风险
