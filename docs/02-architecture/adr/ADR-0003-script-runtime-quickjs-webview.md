# ADR-0003：规则脚本运行时选型（QuickJS 主 + 无头 WebView 兜底）

## 状态

`review` —— **本决策待 M0 可行性验证后定稿**。这是全项目唯一允许被推翻的架构决策。

## 背景

规则脚本是**用户编写的任意 JavaScript**，必须由应用直接执行（[ADR-0002](ADR-0002-embedded-engine-dual-provider.md)）。脚本的形态是"返回配置对象的函数体"，由引擎用 `new Function` 包裹并注入运行时能力：

```js
// 概念示意（非实现代码）
const rule = new Function(wrappedScript)()(selector, getHtml, log, net, …);
rule.getItems(parse(html));   // 用选择器 API 把 HTML 变成数据
```

由此得出两个硬约束：

1. **必须有选择器层**：脚本大量使用 `$('#list .item').each((i, el) => { const $el = $(el); … })`，因此 `$` 不是可选项，也不能用 Kotlin DSL 替代（会违背 P2）。
2. **必须能应对需要真实浏览器的页面**：部分来源用 JS 渲染内容或做人机校验，纯 JS 引擎拿到的是空壳 HTML。

## 备选方案

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **A. 无头 WebView** | 加载页面 → 注入选择器层与脚本 → `evaluateJavascript` 取回 JSON | 与脚本的原生运行环境（浏览器）语义一致；DOM 全可用；天然过 JS 渲染页与部分校验 | 内存 60–120MB/实例；慢；必须串行；只能回字符串；WebView 版本碎片化 |
| **B. QuickJS** | 独立 JS 引擎执行脚本，选择器由 Jsoup 桥接 | 快、内存小（数 MB）、可严格沙箱、可在 JVM 单测 | 需 native so（多 ABI 增加体积）；`Promise`/异步桥需自研；无真实 DOM |
| **C. Rhino / GraalJS** | 纯 JVM 引擎 | 无 native 依赖 | Rhino 仅 ES5（`?.`、`async/await`、模板串会失败）；GraalJS 在 ART 上不可行 |
| **D. 改成 Kotlin DSL** | 用户用 Kotlin 写规则 | 性能最好 | 违背 P2，规则无法由用户在手机上导入维护 |

## 决策

采用 **方案 B 为主通道 + 方案 A 为兜底通道**，形成两级执行结构：

1. **主通道**：QuickJS 执行脚本；注入桥接版 `$`（Jsoup 支撑）；异步能力（`getHtml` / `net.request` / `executeJs`）通过 Promise + JNI 回调实现。
2. **兜底通道**：需要 JS 渲染 / 人机校验 / 用到桥接未覆盖 API 时，切换到**独立进程**的无头 WebView 执行同一份脚本。
3. **降级策略**：桥接层未实现的方法**不抛异常**，记 `unsupported_api` 事件并把该来源标记为"走 WebView 通道"，用户无感。
4. **M0 验证门槛**（满足后本 ADR 才转 `approved`）：
   - 用开发者本地采集的真实页面 HTML 作为黄金样本（不入库，见设计文档 §8.11）；
   - QuickJS + Jsoup 桥接跑真实规则脚本，输出与**人工标注的期望 JSON 逐字段一致**（items / pagination / tags / detail）；
   - 桥接覆盖设计文档 §8.4 列出的选择器与遍历 API 集合；
   - 记录单页解析耗时与内存峰值，作为 M1 的性能基线。

## 理由

1. 纯 QuickJS 性能与内存优势明显，且**可在 JVM 上单测**——对一个"解析逻辑复杂、必须可回归"的项目，这比"跑得更像浏览器"更重要。
2. 纯 WebView 把每个列表页都压到 100MB 级内存，与"300 张图不 OOM"的目标直接冲突。
3. 两级结构让常用路径快、疑难来源也能用，且与 §8.5 的取页策略（先轻后重）天然一致。

## 后果

**正面**

- 常用路径快、可单测、可沙箱化
- 疑难来源有真实浏览器兜底
- 两级策略边界清晰，便于逐来源观测命中率

**负面**

- 需引入 QuickJS 的 native so，APK 体积增加（按 ABI 分包）
- 桥接层是**长期维护面**：Jsoup 与 jQuery/cheerio 的选择器差异需持续补齐
- 同一份脚本有两种执行环境，必须用黄金样本保证结果一致

## 退路（明确写死，避免反复）

若 M0 未达标，**改为主通道也用无头 WebView（方案 A 全量）**：

- 其余设计（数据层、Provider 抽象、契约、UI）**完全不变**；
- 性能指标放宽：列表页首屏 p75 由 <2.5s 放宽到 <5s，内存上限由 300MB 放宽到 500MB；
- 必须新建 ADR 取代本文件，并同步修改设计文档 §8.3 与 §9.1 风险表。
