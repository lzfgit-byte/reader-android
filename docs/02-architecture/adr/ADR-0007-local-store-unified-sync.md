# ADR-0007：本地仓库为唯一数据源，备份/导出/同步统一在仓库层

## 状态

`approved`

## 背景

应用里的数据天然分散：配置在 Room、设置在 DataStore、进度按媒介各存一份、收藏与历史又是独立的表。这种"按功能分数据"的做法在只有配置同步时还能接受（[ADR-0006](ADR-0006-webdav-sync.md) 只同步配置），但现在的需求是：

> 配置信息、软件设置、阅读进度、收藏、历史等，**都落在本地仓库中，可以导入导出，并支持 WebDAV 同步**。

也就是说，用户期待的是一个"整体搬家"的能力，而不是五个互相独立的同步通道。同时新增了文本阅读，进度模型必须能同时表达"读到第几章第几段""看到第几张""播到第几秒"。

## 备选方案

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 各类数据各自同步 | 配置走 `.ghscfg.json`，设置走 `prefs.json`，进度走各自表 | 实现简单，但"搬家"要操作五次，用户容易漏；冲突模型分裂 |
| B. 统一仓库层 + 分层目录 | 一个 `repo.json` 清单 + 若干分片，整体导入导出，分片级同步 | 一次搬家；冲突粒度仍可按分片；需要清单与哈希维护 |
| C. 单文件全量 | 所有数据塞进一个 JSON | 最简单，但每次同步都整包传输，进度频繁变化会放大流量与冲突面 |

## 决策

采用 **方案 B**，并做三项配套决定：

1. **统一进度表** `reading_progress`：以 `kind`（`text`/`image`/`video`）+ `chapterIndex` + `chapterOffset`/`positionMs` 表达全部媒介，替代原来按媒介分表；
2. **设置镜像表** `app_setting`：DataStore 的可导出投影，写入时双写，导出与同步只读镜像，不依赖 DataStore 的内部序列化格式；
3. **同步范围按类别划分**：偏好、配置、进度、收藏、历史参与同步；设备设置（端口、绑定、凭证、代理、缓存上限）与搜索历史默认不参与（见 [local-store](../../03-api/local-store.md) §2）。

## 理由

1. **用户视角是一次搬家**：导入导出与同步的语义应该是"我的东西"，而不是"我的五个东西"。
2. **冲突粒度不需要更细**：配置要 `ask`，进度要 `newer-wins`，收藏要并集——这些差异可以在**分片级**表达，无需每个字段一套规则。
3. **进度必须统一**：文本的"第 3 章第 42 段"、图集的"第 12 张"、视频的"第 300 秒"本质是同一个问题（在这条内容里到哪了），分表会导致"续读"逻辑写三遍。
4. **设置分离是安全需要**：端口、绑定地址、WebDAV 凭证在本机才成立，同步过去既无用也危险。

## 后果

**正面**

- 一次导出即可完整迁移，验收简单（导出→清空→导入→逐项比对）
- 续读/续看逻辑收敛为一套
- 同步失败可按分片局部重试，不会整包失败

**负面（必须正视）**

- **双写一致性**：设置写入 DataStore 与 `app_setting` 两处，需要事务化或"以镜像为准重建"的兜底
- **清单维护**：`repo.json` 的 `updatedAt`/`hash` 必须准确，否则冲突判定失真
- **归一化责任**：`itemUrl` 归一化错了会导致进度对不上，必须有单测与导出后回读校验
- **迁移成本**：`$schema` 升级链是所有导入路径的公共依赖

## 缓解

- 设置双写用"先写 DataStore，成功后写镜像"；启动时校验一致性，不一致以镜像为准回填
- 每次导入/同步后都做一次"主键唯一性 + 归一化幂等"自检
- 归一化规则集中在 `UrlNormalizer`，导出前后各跑一次断言
